02 /

跟随一项任务，
走完交付过程。

示例：整理三份资料，生成带来源的中文报告。下方是交互示意，不会向真实智能体发送任务。

流程示意 · 非实时任务

什么时候会停下来？需要你回答问题、计划涉及额外授权、遇到有证据的外部阻塞，或达到预算时，任务会等待输入或停止。计划模式可按检查结果修正阶段；原生模式续接同一个 Goal。停止请求与停止确认分别记录，未知结果先核对。
03 /

任务有自己的记忆。

任务 ID 标识长期工作。原生模式续接同一个执行器线程；计划模式保留阶段与检查点。发起会话通过显式绑定关联，不靠搜索聊天文字推断。

执行路由

持续任务优先使用经能力探针确认的原生 Goal；小任务可执行一次；需要阶段依赖时使用显式计划。

检查点

任务规格、执行状态、验收结果、证据哈希和日志保存在执行电脑；重启后先核实中断工作的影响。

会话策略

原生模式在同线程接收提示并恢复；计划模式按阶段续接。全局就绪不能代替每个任务的 verified 来源绑定。

运行边界

任务有累计时长和轮次预算，桌面与共享目录分别持锁。停止结果不确定时保留资源占用，先完成对账。

04 /

完成，需要哪些证据？

执行器按结构化格式报告做过什么、观察到什么、产生了哪些文件。taskd 决定下一步状态，并把不同性质的检查结果列入最终报告。

01 · PROGRAM CHECKS

程序可以直接核对的

按明确规则检查实际产物，记录观察值和文件哈希。

  • 文件数量、修改时间与内容
  • 数值是否符合预期
  • 目录是否被修改
  • Windows 界面属性与截图
02 · MODEL REVIEW

需要理解内容的

配置审查模型时，用独立只读会话判断语义与相关性。

  • 报告是否覆盖验收要求
  • 新证据是否推进当前目标
  • 阻塞是否有充分依据
  • 同一问题与证据复用审查结论
03 · REQUESTER CONFIRMATION

最终交付如何判断

未配置模型的语义检查会标为“需确认”，并随报告返回。

  • 读取 report.json 与附件
  • 区分已通过和待确认的项目
  • 检查通信回执与实际成果
  • 关键结果由发起方再次核对
“任务结束”与“全部验收通过”要分别查看。报告可能包含待确认项目；执行节点给出的检查结论也属于执行方报告。消息送达和签名回执不代替业务结果验收。
05 /

通用核心，
按能力接入。

taskd 把执行器、通信、检查器、桌面探针和发起端回传分开。扩展一种软件，需要相应适配器与验证。

组件当前实现作用与边界
执行器Codex / 自定义命令执行工作；Codex 原生 Goal 仅在实际能力探针通过时可用。
通信ANet MCP + CLItaskd 直接读取和回复任务；接任务的节点由 taskd 统一负责回复。
发起端回传Codex 会话适配器逐任务验证来源会话绑定；空闲时请求新轮次核对，并分别记录请求、确认与完成。
检查与环境通用检查器 / Windows 插件按任务配置启用；Windows GUI 运行需要已登录的交互桌面。
门户软件目录Codex / Pi / WorkBuddy / DeepSeek / 自定义软件可接入门户，不等于已具备 taskd 长任务适配；以节点最新上报为准。
